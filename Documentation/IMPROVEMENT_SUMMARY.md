## 改善方針

### 文体の統一

- **対象**：企業内部の開発資料としての専門的で客観的な文体
- **削除対象**：感情的表現、主観的評価、過度な説明口調
- **統一原則**：
  - 「重要です」「特徴です」などの繰り返しを排除
  - 「確認済み」「推定」「未確認」などの限定句を最小化
  - 不必要な前置きと導入を削除
  - 実装に関係しない一般論を削除

### 構成の整理

- **章構成**：大分類（章）→ 関連情報（節）→ 具体内容（項）に統一
- **情報粒度**：一文に複数の異なる情報を詰め込まない
- **参照の明確化**：各資料の役割を維持しつつ、参照先を適切に誘導
- **重複の削減**：同じシステムの説明が複数箇所に存在する場合、概要と詳細の関係を明確化

### 記述形式の統一

- **概要説明**：文章で記述
- **機能・仕様**：表形式（機能名、概要、入力、処理、出力など）
- **クラス設計**：フォーマット化（ファイルパス、責務、主な処理、データ、依存）
- **処理フロー**：Mermaid フローチャート・シーケンス図を使用

### 技術的正確性の維持

- コード確認に基づいた記述
- クラス名、メソッド名、ファイルパス、型名の正確性
- 技術用語の正確な使用
- 仕様・設計・実装・評価の混同防止

## 改善内容の詳細

### 1. AI生成的表現の排除

**削除対象パターン：**
- 同じ内容の繰り返し（各章の冒頭での長い導入）
- 内容のない抽象的な説明
- 不必要な「メリット強調」や定型文
- 「本プロジェクトでは～を実現しています」のような定型文

**例：**
```
【改善前】
「非常に便利で柔軟性の高い設計になっています。システムは効率的に実装されており、
高い拡張性を持つため、将来の変更にも対応しやすいです。」

【改善後】
「敵のパラメータをデータアセットとして管理するため、敵追加時に制御処理を変更しない。」
```

### 2. 冗長な限定句の削除

**削除対象：**
- 「実装確認済み」「設計意図の推定」「未確認」などの前置き
- 「現行の」「確認できない」などの不確実性を示す修飾

**例：**
```
【改善前】
「実装確認済み：剣の近くを押してドラッグすると剣がポインターに追従する。」

【改善後】
「剣の近くを押してドラッグすると、剣がポインターに追従する。」
```

### 3. 曖昧な表現の具体化

**改善例：**
```
【改善前】
「適切に処理する」「効率的に実装する」「高い拡張性を持つ」

【改善後】
具体的な処理内容・条件・構造を明記
「敵の基本数値をScriptableObjectで管理し、敵追加時に既存制御コードを変更しない」
```

### 4. 資料間の整合性確保

**実施内容：**
- 同じシステムの説明が複数資料で重複していないか確認
- 重複がある場合は、概要側と詳細側を明確に分離
- 参照リンクを正確に配置

**例：**
- GameOverview.md：全体概要（1レベル）
- GameDesignDocument.md：ゲーム設計・メカニクス
- GameSpecification.md：詳細仕様（操作・敵・強化）
- SystemArchitecture.md：システム構成図・責務分離
- TechnicalDesign.md：実装設計・技術選定

### 5. 用語・表記の統一

**統一基準：**
- 難易度表記：Easy / Normal / Hard / Extreme / Nightmare（英語で統一）
- 敵名：Slime, Goblin, Zombie, Frog, Troll, Minotaur, Kinoko, Devil, Fire（英語表記）
- 技術用語：Scene, Component, ScriptableObject など英語
- UI：「UI Toolkit」で統一（UI ツールキット、ツールキットなど混用を排除）

### 6. ポートフォリオ・採用向け内容の削除

**削除対象：**
- 技術力のアピールを目的とした表現
- 面接想定質問
- 採用担当者向け説明
- 自己PR的な文章

**保持基準：**
実装上重要な技術・設計・処理の説明は削除せず、企業資料としての技術情報として記録

## 今後の運用

改善済みの資料は、以下の用途で継続運用してください：

1. **チーム開発時の参照資料**：新メンバーのプロジェクト理解
2. **実装確認**：既存機能の仕様確認、バグ分析
3. **機能追加時の設計ガイド**：システム構造の理解、拡張方法の確認
4. **保守性向上**：クラス責務の確認、データフローの追跡

**メンテナンス時の注意：**
- コードの大きな変更があったら、対応資料を更新してください
- 新しいシステム・クラスを追加した場合は、ClassReference.md に追記してください
- 既知問題が解決したら、CodeReview.md と ImprovementPlan.md を更新してください
- 実装内容と資料の乖離が生じないよう、定期的に確認してください
